# 磁盘与文件系统

## 1.1 根分区写满（No space left on device）

**现象**：`df -h` 显示 `/` 使用率超过 90%；应用报 `No space left on device`；日志写入失败。

**排查步骤**

1. 先确认是空间耗尽还是 inode 耗尽：`df -h` 看容量，`df -i` 看 inode。两者要分别判断，inode 用满时 `df -h` 可能只显示 60%。
2. 定位大目录：`du -sh /* 2>/dev/null | sort -rh | head`，然后逐层下钻。
3. 常见元凶按出现频率排序：`/var/log`（日志未轮转）、`/var/lib/docker`（镜像与容器层堆积）、`/tmp`（临时文件未清理）、应用自身的上传目录、`/home` 下的备份文件。

**判定要点**
- 容量满但 inode 正常 → 大文件问题，找大文件。
- inode 满但容量正常 → 大量小文件，通常是 session 文件、缓存碎片、未清理的临时文件。用 `find /path -xdev -type f | wc -l` 统计目录文件数。

**处置**
- 日志类：确认可清理后，`journalctl --vacuum-time=7d` 清理 systemd 日志；应用日志用 `logrotate` 配置轮转。
- 已删除但仍被进程占用的文件（`df` 显示满但 `du` 对不上）：用 `lsof +L1` 找出持有已删除文件的进程，重启该进程释放空间——这是最容易漏掉的一类。
- **不要**直接 `rm -rf` 未知目录，先确认归属。

## 1.2 df 与 du 结果不一致

**现象**：`df -h` 显示使用了 40G，`du -sh /` 只有 20G。

**原因排查顺序**
1. 有进程持有已被删除的文件句柄（最常见）：`lsof +L1 | head`，或 `lsof -n | grep deleted`。
2. 目录被挂载覆盖：`mount | grep` 检查是否有其他文件系统挂载在非空目录上。
3. `du` 因权限跳过部分目录：用 root 或加 `2>/dev/null` 前后对比。

**处置**：第一种情况重启持有句柄的进程即可回收；不要重启整机。

## 1.3 inode 耗尽

**现象**：`df -i` 显示 IUse% 接近 100%，写入报 `No space left on device`，但 `df -h` 还有空间。

**排查**：`for d in /var /tmp /home; do echo -n "$d "; find $d -xdev -type f 2>/dev/null | wc -l; done`

**常见来源**：`/var/spool/postfix` 邮件队列堆积、`/var/lib/php/sessions`、应用产生的海量小 JSON 文件、容器层的碎片文件。

**处置**：定位到具体目录后批量清理；确认是业务文件则改用归档打包减少文件数。inode 数量在格式化时固定，无法在线扩容，只能清文件或重建文件系统。

## 1.4 磁盘 I/O 高（iowait 飙升）

**现象**：`top` 中 `%wa` 长期高于 20%；应用响应变慢；`vmstat 1` 的 `wa` 列偏高。

**排查**
1. `iostat -x 1 3` 看 `%util` 与 `await`：`%util` 接近 100% 说明设备饱和。
2. `iotop -o` 找具体进程（需安装）。
3. 检查是否有大文件拷贝、备份任务、数据库全表扫描在跑。

**处置**：定位到进程后限制其 I/O 优先级（`ionice`），或把备份任务挪到低峰期。若为磁盘本身性能瓶颈，属于容量规划问题。

## 1.5 挂载点失效 / 只读挂载

**现象**：文件系统变成只读，写入报 `Read-only file system`。

**原因**：内核检测到文件系统错误后自动 remount 为只读，通常是磁盘故障或异常断电导致。

**排查**：`dmesg | grep -i -E "ext4|error|remount"` 看内核日志。

**处置**：先止损——把该分区上的服务迁走或停掉，然后 `umount` 后 `fsck` 修复，**不要在挂载状态下强行修复**。若反复发生，说明磁盘硬件有问题，需要更换。

## 1.6 WSL2 / 容器环境下的 df 判读（100% 不等于磁盘满）

**现象**：`df -h` 里出现容量很小（几十 MB）、使用率 100%、inode 也几乎用满的挂载点，
例如 `/usr/src/linux-headers-*-microsoft-standard-WSL2`，Filesystem 显示 `/dev/sdb`，Type 为 `squashfs`。

**结论：这是正常状态，不是故障，不需要任何处置。**

**原因**：WSL2 把内核头文件以只读镜像（squashfs）的形式挂载到该路径。镜像大小固定、文件数固定，
所以 Used 恒等于 Size、IUsed 恒接近 Inodes 总数，`df` 永远显示 100%。该挂载点不可写入，
也不占用根分区的空间。

**属于虚拟/只读文件系统、一律不参与容量判断的类型：**

| 类型 | 典型挂载点 | 说明 |
|---|---|---|
| tmpfs / devtmpfs | /dev/shm、/run、/sys/fs/cgroup | 内存文件系统，按需增长，不会真正写满 |
| squashfs | /usr/src/linux-headers-*、/snap/* | 只读镜像，容量固定，恒定显示 100% |
| 其他伪文件系统 | cgroup、efivarfs、debugfs | 内核接口，容量数值无实际意义 |

**必须与上面区分开的两种特殊情况**：`9p` / `drvfs`（`/mnt/c`、`/mnt/d`）和 `overlay`（容器根目录）
虽然形式特殊，但**容量是真实的**——`/mnt/c` 写满会导致无法向 Windows 盘写入，
容器 overlay 写满会导致容器内一切写入失败。这两类要正常纳入容量判断，
只是扩容路径不同：前者清理 Windows 磁盘，后者调整容器存储配额或清理镜像层。

**只有以下情况才是真正的磁盘风险：**

- 可写文件系统（ext4 / xfs）Use% ≥ 85%，且 `du` 能定位到持续增长的目录；
- inode 使用率 ≥ 85%（`df -i`），表现为"还有空间但创建不了新文件"；
- 根分区写满导致服务写日志失败、进程异常退出。

**禁止的处置**：不要对只读镜像挂载执行 `rm -rf`，不要在 `/usr/src/linux-headers-*` 下清理或编译；
更不要建议 `wsl --unregister`——注销发行版会删除该发行版内的全部数据，不可恢复。
若确实怀疑 WSL 磁盘异常，正确入口是在 Windows 侧检查 `ext4.vhdx` 大小，或用
`wsl --manage <发行版名> --resize <大小>` 扩容，而不是动挂载点内部。
